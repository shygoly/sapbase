# Change: Add Complete Auto-Parts ERP

## Why

`add-minimal-autoparts-template`（已归档）证明了链路能跑通，但它只回答了
"**包能不能让 ERP 动起来**"，没有回答"**能不能生成一个完整的汽配 ERP**"。

现状实测（`schemas/blueprint-semantic.schema.json` + `semantic-runtime`）：

```text
字段类型       8 种（text/number/decimal/boolean/date/datetime/i32/reference）
               —— 没有枚举、没有金额精度、没有单位
字段属性       只有 name / type / required / reference
唯一性约束     协议里根本没有这个概念（grep unique → 0 命中）
主从结构       没有（SalesOrder 只能单行；真实订单是多行明细）
计算字段       没有（金额 = 数量 × 单价 无处安放）
单据运行时     无事务、无单号、无并发控制
状态迁移       只被编译期校验，**没有任何东西执行它**（"确认订单"这个动作不存在）
能力（原子）   1 个（available-inventory）
```

**结论：缺的不是更多字段，而是四层能力。** 把字段从 8 种加到 20 种，
也生成不出"能下多行订单、能按批次发货、能反查批次流向"的汽配 ERP。

## 完整性判据（唯一一条）

> 一个真实的汽配业务动作能走完，且**每一步都由平台判定**：

```text
客户说：「08 款卡罗拉前刹车片，200 套，走宁波华兴的账期」
  ① 车型适配     → 车型/年款 → 命中零件（含替代件）
  ② 可用量       → ATP：现存量 − 预留 − 已承诺 + 在途，**替代件合并**
  ③ 报价         → 客户等级价 / 阶梯价（不是一个固定单价）
  ④ 建单         → **多行订单**（头 + 行），自动分配单号
  ⑤ 信用检查     → 客户额度 − 应收 − 在途
  ⑥ 审批         → 按规则判定（金额/批量）
  ⑦ 确认订单     → 状态迁移**被执行** + 按批次占用库存（FIFO/效期）
  ⑧ 发货 / 开票  → 记账分录被生成
  ⑨ 追溯         → 事后能反查「这批货卖给了谁」（召回要求）
```

这条闭环里的任何一步做不到，就还称不上"完整的汽配 ERP"。

## What Changes

六个阶段，每个阶段有自己的验收门（见 `tasks.md`）。**顺序是依赖关系，不是优先级**：

| 阶段 | 补齐哪一层 | 一句话 |
| --- | --- | --- |
| **P0** 表达力 | 协议（`blueprint-semantic`） | 主从结构、唯一性、金额与精度、枚举、计算字段 |
| **P1** 单据运行时 | `document-runtime` | 单号、事务、状态迁移执行、查询分页 |
| **P2** 判定执行 | `semantic-runtime` 扩展 | 审批求值（含金额合计）、记账分录生成、DB 约束落库 |
| **P3** 汽配能力 | `autoparts-capabilities` | ATP（含批次/替代件）、价格、信用、单位换算、适配匹配 |
| **P4** 追溯与治理 | `autoparts-capabilities` 扩展 | 批次→单据→客户反查、主数据导入、查询视图 |
| **P5** 交付演进 | `blueprint-delivery` 扩展 | 模板版本升级（有数据时怎么办）、多语言/多币种、权限细化 |

## Impact

- 受影响规格：`blueprint-semantic`（新增能力）、`document-runtime`（新增能力）、
  `autoparts-capabilities`（新增能力）；`semantic-runtime` / `blueprint-delivery` 为 MODIFIED
- 受影响代码：`schemas/`、`backend/src/semantic-runtime/`、新增 `backend/src/document-runtime/`、
  `wasm-modules/modules/`（新增若干原子）、`templates/auto-parts-min/` → `templates/auto-parts/`
- **不放松任何既有闸**：所有新增能力都走既有的契约/权限/审计/闸门；新增原子必须过闸 0/1/2/5
- 风险：这是一条**多阶段程序**，不是一次提交。对策见 decisions 第 1 条

## Decisions Made

1. **这是一个 program change，不是一个提交。** 六个阶段各自可独立评审与交付；
   开始某阶段时若发现范围过大，**允许在阶段内拆分子变更** ——
   但"完整性判据"（上面那条业务闭环）与"不放松既有闸"两条不变。
   把它写成一份而不是六份的理由：**缺口的顺序与依赖关系本身就是设计**，
   拆散了看不见依赖（例如"金额合计"既是 P0 的计算字段、又是 P2 审批求值的前提）。
2. **主从结构用"行实体 + 反向引用"，不用内嵌数组。**
   内嵌数组会让查询、索引、审批、批次分配全部变难（每处都要"进数组里找"）。
   行实体是 ERP 的既有共识，也让"行级状态"（部分发货）成为可能。
3. **唯一性必须落到数据库，不能只靠模板校验。**
   我们上一变更明确写了"约束来自模板校验、不来自数据库"——那是最小模板的取舍。
   "完整"必须把**声明式唯一性**翻译成**唯一索引**（`partNo`、单号、OE 号）。
   只在应用层判重，等于把并发下的重复写入交给运气。
4. **金额用定点数 + 一处舍入规则。** `decimal` 要补精度/标度声明与舍入方式，
   且**只在一个地方舍入**。财务金额在四处各舍一次，账永远对不平。
5. **汽配能力只有"纯计算"的做成 Wasm 原子；需要查库的走 query 原子或宿主查询。**
   零能力沙箱是给"给定输入必得输出"的计算用的；跨表查询套进去只会造出一个
   受限的 SQL 方言（那是另一条线，别把它伪装成原子）。
6. **状态迁移的执行放在 `semantic-runtime`**，不新开一个状态机服务 ——
   一张单的"写入"和"推进"是同一个入口的两半，分开会让审计断成两截。

## Out of Scope

- **MES / 生产执行**：排产、工单、车间报工 —— 属制造那条线，与贸易型汽配 ERP 不是一个产品
- **完整总账与税务**：本变更做到"记账分录被生成、可追溯"；
  总账、报表准则、税务申报另立变更
- **多公司/多法人合并报表**
- **前端**：属 `add-chat-first-erp`（模板越完整，交互面越有东西可展示）
- **真实客户数据的迁移实施**：本变更只提供导入能力与判据，不做某个客户的数据工程
