# Design: 完整汽配 ERP 的缺口分层与依赖

## 0. 怎么读这份设计

缺口按**层**列，不按功能列。理由：汽配的功能清单（采购/销售/库存/…）网上一搜就有，
但**哪些是"表达力"缺口、哪些是"运行时"缺口**，决定了工作量与先后顺序 ——
把运行时缺口当表达力缺口做，会写出一个"描述得很完整、一动就散"的模板。

每一层给一条**判据**（怎么算这层补齐了），因为"补齐了"必须可验证。

---

## 1. 五层缺口 + 两条已知

### L1 表达力（协议层）：缺了它连模型都写不出来

| # | 缺口 | 现状 | 判据 |
| --- | --- | --- | --- |
| 1.1 | **主从结构** | 无行项目概念 | 一张单据能声明"头 + N 行"，且行有独立字段与校验 |
| 1.2 | **唯一性** | 协议无此概念（grep 0 命中） | 能声明 `unique`，并**翻译成数据库唯一索引** |
| 1.3 | **金额与精度** | `decimal` 无精度/标度/舍入 | 能声明 `decimal(18,4)` 与舍入方式；**全局一处舍入** |
| 1.4 | **枚举字段** | 只有 `text` | 能声明受限取值集合（单位、类型、来源） |
| 1.5 | **计算字段** | 无 | 能声明派生值（金额 = 数量 × 单价），且**只声明一次** |
| 1.6 | **关系基数** | `reference` 只表达"指向" | 能声明一对多/多对多（BOM 多对多、供应商×零件多对多） |
| 1.7 | **单位与换算** | 无 | 能声明基本单位与包装单位及换算率（箱/套/件） |

### L2 单据运行时：有了表达力还得能跑

| # | 缺口 | 现状 | 判据 |
| --- | --- | --- | --- |
| 2.1 | **单据编号** | 无 | 每张单自动分配业务单号，**并发下不重号** |
| 2.2 | **事务** | 无 | 头 + 行要么全落库要么全不落（现在逐条写） |
| 2.3 | **并发控制** | 无 | 同一库存行被并发修改时，不出现丢失更新（版本/行锁） |
| 2.4 | **状态迁移执行** | flows 只编译、无人执行 | 「确认订单」是一个**真实动作**，且非法迁移被拒 |
| 2.5 | **查询** | 只有最基础的 GET | 分页 / 排序 / 按字段过滤 / 按状态过滤 |
| 2.6 | **关系完整性** | 无 | 被引用的实例不能被删（或删除有明确策略） |

### L3 汽配能力（原子）：行业之所以是行业

| # | 能力 | 现状 | 判据 |
| --- | --- | --- | --- |
| 3.1 | **ATP 可承诺量** | 只有列算术（现−预留+在途） | 含批次/库位/已承诺 + **替代件合并** |
| 3.2 | **价格解析** | 无 | 客户等级价 / 阶梯价 / 最近成交价，优先级明确 |
| 3.3 | **信用检查** | 无 | 额度 − 应收 − 在途 → 结论 + 依据 |
| 3.4 | **批次/序列号分配** | 无 | FIFO/效期策略，且**分配结果可追溯** |
| 3.5 | **单位换算** | 无 | 箱↔套↔件 换算，且不产生浮点误差 |
| 3.6 | **替代件（supersession）** | 无 | 旧件被新件替代时，可用量合并（不是简单相加，要看替代方向） |
| 3.7 | **车辆适配匹配** | 无 | 车型/年款/位置 → 零件候选集 |

### L4 追溯与治理：上线必需，但最能拖

| # | 缺口 | 判据 |
| --- | --- | --- |
| 4.1 | **批次追溯** | 给定批次 → 查到所有相关单据与客户（召回的反向查询） |
| 4.2 | **主数据导入** | 客户的历史零件/客户/供应商能导入，且**非法行逐条报错**（不是整批失败或静默丢弃） |
| 4.3 | **查询视图** | 常用视图（库存/应收/在途）不必靠人写 SQL |

### L5 交付与演进：模板是会变的

| # | 缺口 | 判据 |
| --- | --- | --- |
| 5.1 | **模板版本升级** | 客户已有数据时，模板 1.0.0 → 1.1.0：新增字段有默认值/迁移路径，旧数据不失效 |
| 5.2 | **多语言/多币种/多时区** | 至少不把人民币和美元加在一起（货币是类型的一部分） |
| 5.3 | **权限细化** | 字段级（成本价对销售不可见）/ 单据级 / 数据范围 |

### 两条已知（用户已点名的，列在此以免重复讨论）

| # | 缺口 | 归属 |
| --- | --- | --- |
| K1 | 审批、记账**只声明不执行** | P2：需要受限表达式的求值器（含金额合计）与分录生成 |
| K2 | 约束只来自模板校验，**不来自数据库** | P0/P2：唯一性等约束必须落到 DB（见 decisions 第 3 条） |

## 2. 依赖关系（为什么是这个顺序）

```text
L1 表达力 ──┐
            ├─→ L2 单据运行时 ──→ L3 汽配能力 ──→ L4 追溯治理 ──→ L5 交付演进
P0 计算字段 ─┘        ↑                 ↑
   （金额=数量×单价）  │                 │
         └────────────┴─→ P2 审批求值（要算金额合计，前提是 P0 有计算字段）
```

三处硬依赖，是"把它写成一份变更"的理由：

1. **P2 的审批依赖 P0 的计算字段**：没有"金额 = 数量 × 单价"，审批只能退化成
   "单价超 10 万"这类近似条件（最小模板里已踩过，见 `blueprint-delivery.md` §2.2 的已知缺口）。
2. **P3 的 ATP 依赖 L2 的并发控制**：可用量算准了但并发占用算错，等于没算。
3. **P5 的模板升级依赖 L1 的字段默认值**：没有默认值，新增字段无法对旧数据生效。

## 3. 关键裁决（每条都影响工作量）

### 3.1 主从结构：行实体 + 反向引用

```jsonc
// 而不是内嵌数组
"SalesOrder":     { "fields": [...], "children": ["SalesOrderLine"] },
"SalesOrderLine": { "fields": [...], "parent": { "entity": "SalesOrder", "field": "order" } }
```

- 内嵌数组让查询/索引/审批/批次分配都要"进数组里找"，且行级状态（部分发货）无法表达
- 行实体是 ERP 的既有共识；代价是"头 + 行"的写入需要事务（→ P1 的 2.2）

### 3.2 唯一性：声明式 + 落到 DB

模板声明 `unique` → 迁移生成唯一索引。**不在应用层判重就完事**：
应用层判重在并发下是"先查后写"，两个请求都能查到"不存在"。

### 3.3 金额：定点 + 一处舍入

- 类型 `decimal(p,s)`，禁止用 `number`（JS 的 number 是二进制浮点，0.1+0.2 ≠ 0.3）
- 舍入只在一处（写入前），中间计算保留全精度
- 判据：`0.1 + 0.2` 这类比较在模板层面不可能出现（类型就不允许）

### 3.4 汽配能力的实现形态

| 能力 | 形态 | 理由 |
| --- | --- | --- |
| ATP、价格、信用、换算、替代件合并 | **Wasm 原子**（纯计算） | 给定输入必得输出，正是零能力沙箱的形状 |
| 车辆适配匹配、批次分配 | **宿主查询 + 原子判定** | 需要跨表检索；套进零能力沙箱只会造出受限 SQL 方言 |

**不把查库能力塞进原子**：那是把"零能力"这个最强的安全性质换成"半个数据库客户端"。

## 4. 与既有资产的关系

| 已有 | 本变更怎么用 |
| --- | --- |
| 五层包协议 + 编译器 | L1 的扩展全部走"新增 Schema 字段 + 编译期判据"，不新开协议文件 |
| 语义运行时（记录写入） | P1/P2 在它上面加事务、状态迁移、审批判定（同一个入口，审计不断成两截） |
| 原子契约 + 零能力运行时 + 闸 0/1/2/5 | P3 新增原子全部走既有准入链（复现构建 + 静态闸 + 吊销） |
| 授权与签名（delivery） | P5 的模板升级要**重新签名**（授权绑定租户，升级不能绕过） |
| chat-first 协议（已冻结） | 模板越完整，`interaction-plan` 越有东西可展示 —— 两条线在此汇合 |

## 5. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 程序太大，做到一半停住 | 每阶段有独立验收门；P0+P1 就能让"多行订单"跑起来，不必等 P5 |
| L1 无节制扩张（字段类型越加越多） | 每加一个类型必须回答"它能表达什么现在表达不了的"，并在协议里写明 |
| 唯一约束与既有数据冲突（客户已有重复 partNo） | 迁移必须**先报告冲突清单**再建索引，不允许"建不上就让上线失败" |
| 批次追溯被当成"日志"做 | 判据是**反向查询**（批次→客户），不是"有日志" |
| 汽配能力越做越像垂直行业包 | 原子保持"纯计算"，行业语义留在模板里（能力与行业解耦） |
