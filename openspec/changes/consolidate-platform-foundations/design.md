# Design: 收敛三处 + 通知/待办，以及其余组件的决策

## 1. 工作流收敛：为什么是 semantic-runtime，以及怎么搬

### 1.1 判据：桥的存在就是漂移的来源

```text
workflows（旧）        业务实体状态  ←─ EntityStateUpdaterRegistry ─→  流程实例状态
                       （两处存状态，靠注册表对账；注册表缺一个实体类型就静默不同步）

semantic-runtime（留）  blueprint_records = 蓝图实例；状态字段与流程状态是**同一份数据**
                       （桥不存在，也就不会漂移）
```

这不是"哪套代码更新"的问题：**两处存状态**这件事本身就是错的，
注册表只是把它缝起来。

### 1.2 能力映射表（搬的是能力，不是代码）

| 旧 `workflows` 的能力 | 搬到哪 | 判据 |
| --- | --- | --- |
| 定义 CRUD（`/workflows`） | 蓝图 `flows.json` + 编译期校验 | 模板里声明即可，不再有"定义表" |
| 启动实例（`/workflows/:id/start`） | 写一条 `blueprint_records` | 写入即实例（校验链同 P1） |
| 迁移（`/workflows/:id/transition`） | `POST .../records/:entity/:id/transition` | 已存在；非法迁移拒绝 |
| 迁移历史（`/workflows/:id/history`） | 迁移审计 + 历史读回接口 | 审计可查，且能按实例读回序列 |
| AI 建议迁移（`suggested-transitions`） | 保留为**建议**（不改状态） | 建议与执行分离，建议不落库状态 |
| 自动迁移（`@Cron` job） | 平台调度 + 蓝图条件 | 定时任务只调用同一迁移入口 |
| 状态图 / 时间线（前端） | chat-first 交互面 + 现有只读接口 | 见 §1.3 |

### 1.3 收敛顺序（先双跑，再删）

```text
第 1 步  双跑：旧 `/workflows` 保持可用；新蓝图接口补齐"存量前端需要的那几个读接口"
第 2 步  前端切换：admin/workflows 改为调用蓝图接口（页面形态不变，只换数据源）
第 3 步  停用：旧模块从 app.module 摘除，保留路由 410 + 迁移指引
第 4 步  删除：删除两棵旧树；workflow_* 三表给出导出/归档脚本（不静默丢弃）
```

**为什么必须双跑**：前端 5 个组件 + 211 行 API 客户端在用旧接口；
直接替换等于让管理界面在收敛期间不可用。

## 2. 通知与待办：先 Outbox

### 2.1 现状为什么不能补

```text
notification.service.ts：pendingNotifications = new Map(...)
  → 重启即失、已读状态不持久、没有投递保证、**零业务生产者**
```

补它之前必须先有"事件不丢"这件事，否则通知只是"在线时可能收到"的东西 ——
而审批、发货这类事件**丢一条就是业务事故**。

### 2.2 Outbox 的形状

```text
业务写入（迁单 / 审批 / 导入）在同一事务里写一条 outbox 行
  → 投递器（独立进程或定时器）读未投递行 → 投递给订阅者 → 标记已投递
订阅者：通知、追溯、外部 webhook（本变更只做前两个，第三个留投递点）
```

三条硬要求：

1. **与业务写入同事务**：否则业务成功、事件丢失（这正是进程内 EventBus 的毛病）。
2. **投递至少一次 + 幂等键**：重复投递比丢失好；订阅者按事件 id 幂等。
3. **可查**：outbox 行可查状态（待投/已投/失败），失败要有重试计数与最后错误。

### 2.3 通知与待办的分工

| | 通知（推） | 待办（拉） |
| --- | --- | --- |
| 回答什么 | "刚发生了什么需要你知道" | "现在有哪些事等我做" |
| 存储 | `notifications` 表（已读持久） | 聚合查询（审批链 pending + 分配给谁） |
| 与审批的关系 | 产生一条通知 | 是审批链的**入口**（现在缺的就是它） |

**待办是优先的那个**：审批人不知道"有哪些在等我"，通知再准也没用。

## 3. AI 输出 → 蓝图五层

### 3.1 只做转换，不新定义协议

```text
ai_module_definitions.mergedDefinition（六步合并产物）
        ↓ 转换器（纯函数，可测）
semantic.json / flows.json / rules.json / experience.json
        ↓ 既有链
打包 → 编译（IR）→ 授权 → 签名 → 交付
```

判据：**AI 生成的结果进得了既有编译/交付链**。进不了，说明它只是草稿，
那就得在协议层补，而不是在 AI 那条线上再长一套。

### 3.2 转换器必须"会说不知道"

AI 产物里缺的部分（没有规则、没有经验策略）**不许编**：
缺 `rules.json` 就产出一个不含规则层的包（既有链允许可选层）。
编出来的规则比没有规则更危险 —— 它会被当成真的。

## 4. 其余大组件的决策（"其他你来决策"，此处逐条给出结论与触发条件）

| 组件 | 决策 | 理由 / 触发条件 |
| --- | --- | --- |
| 报表 / 看板 | **延后，排第一** | 数据已经有了却没有出口；触发条件：第一个真实客户上线 |
| 单据输出（PDF / Excel / 打印） | **与报表同批** | 两者共用"输出层"（模板 + 渲染 + 存储），分开做等于做两遍 |
| 出站集成（webhook / 连接器） | 现在不做，但 **Outbox 留投递点** | 没有具体对接方时做等于猜；N 阶段顺手把第三个订阅者位置留出来 |
| 数据范围（部门 / 仓库级） | **不做**（与上次判定一致） | 需要可信的用户属性模型；从请求参数取范围 = 让调用方自己授权 |
| 可观测性 | **不上 OTel 栈**，改做结构化日志 + 关键路径耗时 | 当前规模不值一套栈；而 N 阶段的事件投递必须有排障手段，所以**在这一阶段做最小集** |
| 部署形态（Docker / K8s） | **延后** | 触发条件：第一个客户要私有部署；在那之前 CI 只做构建与测试 |
| 多币种汇率 / 时区 | 现在不做（货币类型已进协议） | 触发条件：第一张真实跨境单据 |
| 市场 / 结算 | **不做** | 授权协议已有（能绑租户、能签名），但定价与分成是商业决策，不是技术缺口 |
| 搜索 / 图 / 向量 | **不做** | 触发条件：设计期 AI（Context Compiler）真要做 —— 那时它才有用途 |
| 移动端 / 离线 | **不做** | 触发条件：仓库/车间场景被验证 |

**一条统一判据**（供以后再筛）：**它是不是让已有能力闭环？**
上面排在前面的三项（报表、输出、出站集成）都是"已有数据没有出口"，
排在后面的（市场、搜索、移动端）都是**新能力**。

## 5. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 前端在用的工作流被拆坏 | 双跑 → 切换 → 停用 → 删除，四步，每步可回退 |
| 存量 `workflow_*` 数据丢失 | 只导出/归档，不物理删除；导出脚本进 tasks |
| Outbox 成为"第二个事件系统" | 它**替换**进程内 EventBus 的跨进程部分，不并存两套发布路径 |
| AI 转换器变成第二套协议 | 转换器只做映射；缺层就缺层，不发明字段 |
| 收敛期间新旧两套都在跑，审计分裂 | 双跑期两条路径都写同一条 `audit_logs`，用 `source` 字段区分 |
